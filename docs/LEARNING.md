# 🧠 파인튜닝 Vibe Learning 가이드

이 문서는 `edu-llm-colab-unsloth`에서 쓰는 기술들을 **"왜·언제·무엇을 조절하나"** 관점으로 정리합니다.
완벽한 이론서가 아니라, **돌려보면서 감을 잡는(vibe learning)** 안내서입니다.
각 항목은 `맥락 → 왜 → 언제 → 조절 노브(알아야 할 것)` 순서로 되어 있습니다.

> 읽는 법: 처음엔 **큰 그림**과 **치트시트**만 보고 바로 노트북을 돌리세요.
> 결과가 이상할 때 해당 기술 섹션으로 돌아와 "노브"를 확인하면 됩니다.

---

## 0. 큰 그림 — 멘탈 모델

파인튜닝은 **"이미 똑똑한 모델에게 우리 말투·행동을 가르치는 것"** 입니다.
지식을 0부터 넣는 게 아니라, **행동 양식(시나리오별 응답 방식)** 을 입히는 작업이에요.

```
사전학습 모델(Qwen2.5)   ← 이미 언어/지식을 앎 (남이 수백억 들여 학습)
      │
      │  4bit로 압축해서 작은 GPU에 올림 (bitsandbytes)
      ▼
  + LoRA 어댑터          ← "여기만 살짝 고칠게" (PEFT, 전체의 1% 미만만 학습)
      │
      │  교육 데이터로 행동을 학습 (TRL SFTTrainer)
      ▼
  파인튜닝된 튜터 모델     ← 소크라테스 문답·단계 채점 등 우리 시나리오대로 답함
```

핵심 직관 3가지:
1. **데이터가 8할이다.** 하이퍼파라미터보다 데이터 품질·양·다양성이 결과를 좌우합니다.
2. **작게 바꾼다.** 전체를 다시 학습하면 모델이 원래 알던 걸 까먹습니다(망각). LoRA는 그래서 일부만 건드립니다.
3. **과적합을 경계한다.** 같은 데이터를 너무 오래 외우면 새 질문에 약해집니다. loss와 샘플 출력으로 감시합니다.

## 1. Google Colab + GPU

- **맥락**: 학습엔 GPU가 필요한데, 개인 PC엔 보통 좋은 GPU가 없습니다.
- **왜**: Colab은 무료로 **T4 GPU(VRAM 16GB)** 를 빌려줍니다. 설치 없이 브라우저에서 돌아갑니다.
- **언제**: 거의 항상. 로컬에 RTX 3090/4090급이 있으면 로컬도 가능.
- **알아야 할 노브**:
  - `런타임 → 런타임 유형 변경 → T4 GPU` 를 **반드시** 먼저 선택 (안 하면 CPU로 돌아 엄청 느림).
  - **VRAM 16GB가 한계선.** 모델이 크거나 batch가 크면 `CUDA out of memory(OOM)`. → 4bit·작은 batch·짧은 seq로 해결.
  - 무료 세션은 몇 시간 후 끊김. 중요한 결과는 구글 드라이브에 저장(노트북 8번 셀).

---

## 2. 사전학습 모델 (Qwen2.5 / Llama-3.2)

- **맥락**: 백본 모델을 고릅니다. 우리는 `unsloth/Qwen2.5-1.5B-Instruct` 기본.
- **왜**: 작을수록(0.5B~1.5B) 무료 GPU에서 빠르고 OOM이 안 납니다. Qwen은 한국어가 좋습니다.
- **언제**: 프로젝트 시작 시 1번. 결과가 너무 약하면 더 큰 모델로, 너무 느리면 더 작은 모델로.
- **알아야 할 노브**:
  - **`-Instruct`(또는 -Chat) 버전을 쓰세요.** 이미 대화/지시 따르기를 배운 모델이라 파인튜닝이 쉽습니다.
    (`Base` 모델은 자동완성만 알아서, 처음부터 대화를 가르쳐야 함 → 어려움)
  - **크기 트레이드오프**: 0.5B(빠름·덜 똑똑) ↔ 1.5B(균형) ↔ 3B+(똑똑·느림·OOM 위험).
  - 모델마다 **채팅 템플릿**이 다름 → 4번 항목 참고.

---

## 3. 양자화 (bitsandbytes, 4bit) = QLoRA의 Q

- **맥락**: 모델 가중치는 보통 16bit 숫자. 1.5B 모델이면 ~3GB, 7B면 ~14GB.
- **왜**: 각 숫자를 **4bit로 압축**하면 메모리가 ~4배 줄어 작은 GPU에 큰 모델이 올라갑니다.
- **언제**: 무료/소형 GPU에서 학습할 때 거의 항상 (`load_in_4bit=True`).
- **알아야 할 노브**:
  - `load_in_4bit=True` 켜면 메모리 절약, 끄면(16bit) 약간 더 정확하지만 VRAM 많이 먹음.
  - **4bit + LoRA = QLoRA**. 압축된 모델은 그대로 두고 LoRA 어댑터만 학습하는 조합 = 우리가 쓰는 방식.
  - 품질 손실은 보통 미미함. OOM 나면 가장 먼저 켜는 스위치.

---

## 4. 데이터 포맷 & 채팅 템플릿

- **맥락**: 모델은 `시스템/사용자/어시스턴트` 역할이 특수 토큰으로 구분된 형식으로 학습됐습니다.
- **왜**: 형식을 안 맞추면 모델이 "대화"로 인식 못 해 학습이 망가집니다.
- **언제**: 데이터 준비 단계(노트북 5번 셀)마다.
- **우리 매핑**:
  | 우리 필드 | 역할 | 의미 |
  |---|---|---|
  | `instruction` | system | **시나리오 유형 지정** → 모델이 상황을 구별하는 핵심 |
  | `input` | user | 학생/사용자 발화 |
  | `output` | assistant | 모델이 학습할 이상적 답변 |
- **알아야 할 노브**:
  - `get_chat_template(tokenizer, chat_template="qwen-2.5")` — 모델 계열에 맞는 템플릿 선택. 모델 바꾸면 이것도 바꿔야 함(`llama-3.1` 등).
  - **`instruction`에 시나리오를 명확히 적을수록** 시나리오별로 다르게 행동하도록 잘 학습됩니다.
  - 학습은 보통 **assistant 부분(정답)에만 loss를 줍니다.** (질문까지 외우게 하지 않음)

## 5. LoRA / PEFT — "어디를, 얼마나" 고칠까

- **맥락**: 모델 전체(수십억 파라미터)를 학습하면 메모리·시간이 폭발하고 망각이 생깁니다.
- **왜**: **LoRA**는 기존 가중치는 얼리고, 작은 보조 행렬(어댑터)만 학습합니다. 학습량이 전체의 **1% 미만**.
- **언제**: 항상(우리 기본). 결과를 더 끌어올리고 싶을 때 `r`을 키웁니다.
- **알아야 할 노브** (노트북 4번 셀):
  - **`r`(rank)**: 어댑터 용량. **클수록 표현력↑·메모리↑·과적합 위험↑.** 8~16이 무난, 더 배우게 하려면 32~64.
  - **`lora_alpha`**: 어댑터 영향 강도. 보통 `r`과 같게(16/16) 두면 됨.
  - **`target_modules`**: 어디에 어댑터를 붙일지. 우리는 attention+MLP 전부(`q,k,v,o,gate,up,down`) → 성능 좋음.
  - **`lora_dropout`**: 과적합 방지용. 데이터가 적으면 0.05~0.1, 많으면 0.
  - 직관: **데이터 적음 → r 작게, dropout 켜기 / 데이터 많고 복잡 → r 크게.**

---

## 6. 학습 = SFT (TRL `SFTTrainer`)

- **맥락**: SFT(지도 파인튜닝) = "질문→이상적 답변" 쌍을 보여주며 따라 하게 함.
- **왜**: 우리가 원하는 행동(시나리오별 응답)을 가장 단순·확실하게 가르치는 방법.
- **언제**: 메인 학습 단계(노트북 6번 셀).
- **알아야 할 노브(하이퍼파라미터)** — 가장 자주 만지는 곳:
  | 파라미터 | 의미 | 직관 |
  |---|---|---|
  | `learning_rate` | 한 번에 얼마나 크게 배울지 | LoRA는 보통 **2e-4**. 발산하면 ↓(1e-4), 너무 안 변하면 ↑ |
  | `num_train_epochs` | 데이터를 몇 바퀴 볼지 | **1~3**이 보통. 많이 돌리면 과적합 |
  | `max_steps` | 총 스텝 수(데모용) | 실험엔 60, 실제 학습은 epochs로 바꾸기 |
  | `per_device_train_batch_size` | 한 번에 처리할 샘플 수 | 크면 안정·VRAM↑. T4는 보통 2 |
  | `gradient_accumulation_steps` | batch를 나눠 누적 | "유효 batch = batch×accum". VRAM 아끼며 큰 batch 효과(2×4=8) |
  | `warmup_steps` | 초반 천천히 가속 | 5~10. 초반 발산 방지 |
  | `lr_scheduler_type` | learning rate 감소 곡선 | `linear`/`cosine` 무난 |
  | `weight_decay` | 과적합 억제 | 0.01 정도 |
  | `max_seq_length` | 입력 최대 길이(토큰) | 길수록 긴 글 처리·VRAM↑. 2048 기본, 요약/지문은 ↑ 필요 |
- **읽는 법(학습 로그)**: `loss`가 **완만히 감소**하면 정상. 들쭉날쭉/증가 → lr 너무 큼. 0에 수렴 → 과적합 의심.

## 7. 데이터 (HuggingFace Datasets) — 사실상 가장 중요

- **맥락**: `scripts/fetch_hf_datasets.py`가 16개 실제 데이터셋을 받아 20시나리오 포맷으로 변환.
- **왜**: 모델 품질의 8할은 데이터. 수제 예시 몇 개로는 절대 안 됩니다(그래서 HF 실데이터 사용).
- **언제**: 학습 전 매번. 결과가 약하면 **데이터부터** 늘리고 점검.
- **알아야 할 노브**:
  - **양**: 시나리오당 수천 개 이상이 이상적. `--per-source 8000` 같은 값으로 조절.
  - **다양성**: 한 소스만 많으면 편향. `--only`로 섞거나 소스별 수를 맞추기.
  - **균형**: 특정 시나리오가 과대표집되면 그 행동만 잘함. 분포 로그 확인.
  - **언어**: `lang=en` 데이터는 **행동/형식**은 가르치지만 한국어 출력엔 약함 → 비중 낮추거나 번역.
  - **라이선스**: 상업용이면 Apache-2.0/MIT 우선. `CC-BY-ND`(파생금지)는 학습 부적합(평가만).
  - **streaming**: 193k짜리도 전체 다운로드 없이 N개만 추출(우리 스크립트가 처리).

## 8. 추론 & 평가

- **맥락**: 학습 후 진짜 시나리오 톤이 나오는지 확인(노트북 7번 셀).
- **왜**: loss 숫자만으론 품질을 모릅니다. **직접 질문해 보는 게 진짜 평가**.
- **언제**: 학습 직후, 그리고 데이터/설정 바꿀 때마다 비교.
- **알아야 할 노브**:
  - **`temperature`**: 답변의 무작위성. 낮으면(0.1~0.3) 일관·딱딱, 높으면(0.7~1.0) 창의·산만. 교육용은 보통 낮게.
  - **`max_new_tokens`**: 답변 최대 길이.
  - **과적합 신호**: 학습 데이터엔 완벽한데 약간 다른 질문엔 엉뚱 → epochs/r 줄이거나 데이터 늘리기.
  - **정량 평가(선택)**: `scenarios.json`의 `expectation`을 기준으로 시나리오별 채점.

## 9. 저장 & 내보내기

- **맥락**: 학습 결과를 재사용/배포(노트북 8번 셀).
- **왜**: 다음에 또 학습하지 않으려고. 다른 도구에서 쓰려고.
- **언제**: 만족스러운 모델이 나왔을 때.
- **알아야 할 노브**:
  - **LoRA 어댑터만 저장**(수십 MB): 가볍고 빠름. 추론 시 베이스 모델 + 어댑터 함께 로드.
  - **GGUF로 내보내기**: `Ollama`/`LM Studio`/`llama.cpp`에서 로컬 실행. 시간 좀 걸림.
  - **merge**: 어댑터를 베이스에 합쳐 단일 모델로(배포 단순, 용량 큼).
  - 구글 드라이브 백업 권장(Colab 세션은 사라짐).

## 🎛️ 치트시트 — 증상별 "어떤 노브를 돌릴까"

| 증상 | 1순위 조치 | 2순위 |
|------|-----------|-------|
| `CUDA out of memory(OOM)` | `load_in_4bit=True`, batch=1 | `max_seq_length`↓, `r`↓, 더 작은 모델 |
| 학습이 너무 느림 | 더 작은 모델(0.5B), `max_steps`↓ | batch↑(여유 있으면) |
| loss가 안 줄어듦 | `learning_rate`↑(예 3e-4) | `r`↑, 데이터 품질 점검 |
| loss가 발산/들쭉날쭉 | `learning_rate`↓(1e-4), `warmup`↑ | batch↑ |
| 시나리오 구분을 못 함 | `instruction`을 더 명확히 | 시나리오별 데이터 균형 맞추기 |
| 학습 답엔 완벽, 새 질문엔 엉뚱(과적합) | epochs↓, 데이터↑ | `r`↓, `lora_dropout`↑ |
| 한국어가 어색함 | 한국어 데이터 비중↑ | `lang=en` 소스 줄이기 |
| 답이 너무 짧음/길음 | `max_new_tokens` 조절 | 데이터의 output 길이 점검 |
| 답이 매번 딴소리(불안정) | `temperature`↓ | — |
